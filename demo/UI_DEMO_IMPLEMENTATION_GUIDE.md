# UI Demo 到真实项目实现说明

> 本文档用于指导将 `demo/ui-dashboard-prototype/` 的 UI Demo 迁移到真实桌面项目 `tauri-ui/`，并连接现有 Python/Tauri 后端。
>
> **核心原则：UI Demo 只提供界面参考，真实后端能力优先。**  
> Demo 中的假数据、模拟状态、定时循环和未被后端支持的交互，不得直接作为真实功能实现。

**文档状态**：实现约束  
**适用日期**：2026-10-09  
**适用范围**：`demo/ui-dashboard-prototype/` 到 `tauri-ui/` 的页面与交互迁移  
**不包含**：具体代码改造计划、排期、版本发布计划

## 1. 事实来源与优先级

真实项目实现时，信息来源按以下优先级处理：

1. Python 后端业务逻辑与数据模型。
2. Tauri/PyTauri command 定义与返回结构。
3. `tauri-ui/src/lib/ipc.ts` 中的类型化 IPC 封装。
4. `tauri-ui/src/store.ts` 中的全局运行状态。
5. `tauri-ui/src/pages/*` 中已经存在的真实页面行为。
6. `demo/ui-dashboard-prototype/` 中的视觉、布局、信息层级和交互意图。

如果 Demo 与后端能力冲突：

- 必须修改 UI 以符合后端；
- 不得为了保留 Demo 交互而虚构新的后端状态；
- 不得用静态假数据掩盖真实数据缺失；
- 不得向用户承诺后端尚未实现的能力；
- 如果某项能力暂时没有后端支持，应隐藏、禁用，或明确标记为“暂不可用”，不能伪装成已完成。

以下内容可以作为真实项目的界面参考：

- 运行页作为默认首页；

- 历史记录的筛选、展开详情、复制日志入口；

- 错误场景的内联提示、日志复制和问 AI 入口；
- 按钮、状态标签、警告色和危险操作的视觉语义；
- 抽屉、确认弹窗、FAQ 展开等通用交互形式。

以下内容不能视为真实数据或真实状态：

- Demo 中的审核队列初始数据；
- Demo 中配置页的本地状态；
- Demo 中帮助页的固定诊断信息和最近错误摘要。

## 4. 运行页实现规则

### 4.1 启动、停止与运行状态

真实运行必须使用：

- `ipc.startRun(config, progressChannel, logChannel)`
- `ipc.stopRun()`
- `ipc.isRunning()`
- `ProgressEvent`
- 日志 Channel

后端 `start_run` 会在启动前校验：

- 用户名不能为空；
- 当前简历必须存在；
- LLM API Key 必须已配置；
- LLM model 必须已配置；
- 当前不能已有其他运行任务。

真实 UI 必须在开始前或收到后端错误时明确展示这些校验结果，不能只显示一个模糊的“启动失败”。

### 4.2 Dry Run 必须在启动时确定

运行配置中的 `dryRun` 会传给后端，并决定本次运行是否真实发送。一次运行开始后，该模式不可改变。

因此：

- 运行中禁止切换 Dry Run / 真实发送；
- 运行中应禁用相关表单控件；
- 真实发送必须保留明确的危险提示和二次确认；
- 重新运行时才允许重新选择模式；
- UI 展示的模式必须对应本次实际启动时的 `config.dryRun`。

Demo 中可以在任意时刻切换模式只是为了展示视觉变化，真实项目不得照搬。

### 4.3 当前不支持真正的暂停/继续

Demo 提供：

- “暂停队列”
- “继续运行”

但当前后端只提供 `stop_run`，其实现是取消当前异步任务。现有后端没有暂停 checkpoint、恢复游标或 `resume_run` command。

因此真实项目必须遵守：

- 不得把 `stop_run` 叫作“暂停”；
- 不得在停止后显示“继续运行并从原位置恢复”；
- 如果暂时没有暂停能力，应使用“停止任务”或“取消本次运行”；
- 如果产品确实需要暂停/继续，必须先增加后端协议和可恢复运行状态，再接入 UI。

### 4.4 进度必须由真实事件解释

后端当前事件类型为：

- `browser_started`：浏览器启动；
- `login_ok`：登录态确认；
- `job_found`：找到岗位/JD；
- `job_skipped`：岗位被跳过，并携带原因、分数、阈值等信息；
- `scoring_degraded`：评分降级或 fail-open；
- `letter_sent`：招呼语处理完成，携带 `sent`、`dry_run` 或 `blocked` 状态；
- `feed_exhausted`：推荐岗位流耗尽；
- `loop_ended`：本轮完成、取消或出错；
- `error`：未捕获错误及阶段信息。

真实 UI 应根据这些事件更新：

- 当前运行状态；
- 当前岗位索引；
- 事件时间线；
- 跳过和拦截原因；
- Dry Run、真实发送和失败状态；
- 完成、取消、错误三种结束状态。

不能使用 Demo 中的固定阶段计时器来推断业务进度。特别是：

- 不应把每一次日志或定时 tick 都当作“扫描了一个岗位”；
- 不应把固定的 150 条作为真实队列总数；
- 不应在中途停止后把进度显示为 100%；
- 不应把 `letter_sent` 的所有状态都显示成“已发送”。

### 4.5 运行页的“审核队列”边界

Demo 设计了人工审核队列，并允许：

- 编辑招呼语；
- 重新生成；
- 审核通过并发送；
- 跳过；
- 查看 JD。

当前后端真实运行流程是：

1. 抓取 JD；
2. 使用简历内容进行匹配；
3. 调用 LLM 生成招呼语；
4. 校验招呼语；
5. Dry Run 时记录但不发送；
6. 非 Dry Run 且校验通过时直接发送；
7. 写入审计日志。

当前没有逐条审核、编辑后重新校验、单条批准发送的 IPC command。因此真实项目不能直接把 Demo 审核队列当作已经存在的后端功能。

真实 UI 的处理方式：

- 可以保留“审核/预览”的视觉方向；
- 只能展示后端已经产生并通过事件或历史记录提供的数据；
- 没有对应 command 时，不显示会触发真实发送的“审核通过并发送”按钮；
- 不能声称运行中的新生成内容会自动进入可操作的前端审核队列；
- Dry Run 的实际语义是“生成、校验、记录，但不发送”，不是“前端逐条等待审核”。

## 5. 简历功能实现规则

当前后端提供：

- `ipc.getResume()`
- `ipc.setResume(path)`
- `ipc.setResumeBytes(filename, dataBase64)`

支持的真实行为：

- 读取当前简历文件名和路径；
- 拖拽 PDF 后复制到应用数据目录的 `resume/`；
- 通过文件选择器读取 PDF 字节并保存；
- 校验文件是否为可读取 PDF；
- 启动运行前检查简历是否存在。

Demo 中以下内容目前不能直接当作真实功能：

- “解析中…”的模拟计时；
- 固定的文件大小和更新时间；
- 固定的“312/318 切片”；
- 固定的向量库状态；
- 固定的 RAG 召回样例；
- “查看完整召回样例”按钮。

原因是当前 UI IPC 没有提供：

- 简历解析进度；
- 当前解析状态；
- 切片数量；
- 召回结果；
- 结构化简历 profile；
- 清理或刷新向量库的 command。

真实项目应至少保证：

- 上传成功后展示后端返回的真实文件名；
- 上传失败时展示后端错误；
- 运行中禁止替换简历；
- 没有简历时明确阻止启动；
- 不展示无法从后端读取的解析细节。

如果后续需要展示 RAG 或结构化简历，必须先定义对应后端返回结构和 IPC，再设计页面字段。

## 6. 历史记录与成本数据规则

### 6.1 招呼语记录

历史数据来自：

- `ipc.getLetters(limit)`
- 后端 `logs/letters.jsonl`

真实 `LetterRecord` 字段包括：

- `ts`
- `provider`
- `model`
- `dry_run`
- `validation_ok`
- `validation_reasons`
- `sent`
- `letter_len`
- `job_description`
- `letter`

字段含义：

- `dry_run: true` 表示本次只生成和记录，不真实发送；
- `sent: true` 才表示已经记录为真实发送成功；
- `validation_ok: false` 表示招呼语校验失败；
- `validation_reasons` 是后端校验失败原因；
- `job_description` 是岗位描述原文或后端保存的内容；
- `letter` 是实际生成的招呼语内容。

Demo 中的以下字段当前后端没有直接提供：

- 公司名称；
- 岗位名称；
- 匹配度；
- 运行批次；
- 发送失败类型；
- 审核人；
- 前端审核状态。

真实页面不能从 `job_description` 中不可靠地猜测公司名和岗位名，也不能把假数据中的字段继续展示为真实字段。

### 6.2 LLM telemetry

成本与调用汇总来自：

- `ipc.getTelemetrySummary()`
- `logs/llm_calls.jsonl`

真实数据包括：

- 总调用次数；
- 总成本；
- 按 provider 汇总；
- 输入 token；
- 输出 token；
- provider 成本；
- 平均延迟等后端汇总信息。

Demo 中固定的“近 7 天调用”“¥3.27”“已发送 32 条”等数字不得保留到真实项目。

如果后端没有提供时间范围过滤，UI 不得把数据标注为“近 7 天”；应使用后端实际统计范围，例如“最近 1000 次调用”。

### 6.3 刷新与空状态

历史页面刷新必须重新调用后端，而不是只改变本地时间文本。需要处理：

- 文件不存在；
- 文件为空；
- 单行 JSON 损坏；
- IPC 读取失败；
- 有数据但 telemetry 为空。

## 7. 配置页实现规则

配置页必须使用现有 IPC：

- `getLlmConfig`
- `setLlmConfig`
- `getEnvFields`
- `writeEnvFields`
- `getLanguage`
- `setLanguage`
- `getLetterPrompt`
- `setLetterPrompt`

### 7.1 LLM 配置

真实 LLM 配置包括：

- `LLM_BASE_URL`
- `LLM_MODEL`
- `LLM_API_KEY`
- 后端提供的 provider preset
- `hasKey` 状态

要求：

- API Key 不得由前端伪造脱敏值；
- 已配置时只显示“已配置”，不能回传或展示明文；
- 留空 API Key 时应遵循后端约定，不能擅自覆盖已有 key；
- 选中 preset 只是填写 base URL 和 model，不代表已经配置 API Key；
- 保存失败必须显示真实错误；
- 保存成功后应重新读取后端配置，避免只更新前端假状态。

### 7.2 通用环境字段

当前后端通用配置字段来自 `field_meta()`，包括：

- `BOSS_USR_NAME`
- `BOSS_LABEL`
- `BOSS_CHROME_PROFILE`
- `BOSS_MIN_MATCH_SCORE`
- `BOSS_MIN_KEYWORD_MATCH`
- `BOSS_EXCLUDE_KEYWORDS`
- `LOGLEVEL`

Demo 只展示了其中一部分字段，真实项目必须以 `getEnvFields()` 返回结果为准，不能用 Demo 字段列表覆盖后端字段列表。

### 7.3 招呼语 Prompt

真实 Prompt 使用：

- `getLetterPrompt()`
- `setLetterPrompt(prompt)`

空字符串表示恢复内置默认 Prompt。UI 应：

- 展示真实当前自定义值；
- 将后端返回的默认 Prompt 作为占位或参考；
- 支持恢复默认；
- 保存后重新读取；
- 不把 Demo 中的固定 Prompt 作为真实默认值。

### 7.4 界面语言

真实项目支持 `zh` / `en`：

- 切换后立即更新界面；
- 通过 `setLanguage` 持久化；
- 启动时通过 `getLanguage` 恢复；
- 保存失败不应阻断当前会话。

Demo 只展示中文，不能据此删除真实项目已有的中英文能力。

### 7.5 配置与运行状态同步

真实项目中：

- 运行页的用户名和岗位标签来自全局 store，并由配置读取结果初始化；
- 运行参数可能在运行页直接编辑；
- LLM 配置由配置页管理，运行页只读展示；
- 保存配置后，后端会同步 `.env` 与进程内 `os.environ`，下一次运行即可生效。

不得复制 Demo 中配置页独立维护一套 `cfg`、运行页再维护另一套运行配置的做法，避免用户看到“已保存”但运行仍使用旧值。

## 8. 帮助、诊断和错误处理规则

当前后端已提供：

- `getAiHelpReport(logs)`
- `getLogDir()`
- `openIssuesPage()`
- 运行页的实时日志 Channel；
- `error` 和 `loop_ended(reason="error")` 事件。

真实项目应：

- 使用当前运行日志和真实环境信息生成问 AI 文本；
- 不在前端硬编码 Chrome 版本、简历切片数量、LLM 状态和日志目录；
- API Key 只展示“已配置/未配置”，不得进入诊断文本；
- 复制日志必须真正调用剪贴板 API；
- 剪贴板失败时显示失败反馈；
- 可向用户展示日志目录路径，但不自动上传日志；
- 错误、取消、正常完成要使用不同文案。

Demo 帮助页中的以下内容不能直接照搬：

- 固定 `DIAGNOSTIC` 检查列表；
- 固定 `RECENT_ERRORS`；
- 固定 `HELP_PROMPT`；
- 没有实际复制行为的“复制完整错误日志”按钮；
- FAQ 中引用但页面不存在的“检查登录态”或“环境体检重试”按钮。

FAQ 可以保留，但每条答案必须对应真实页面和真实操作。不存在的按钮必须删除或改成当前可执行的路径。

## 9. 顶栏、导航和刷新规则

### 9.1 顶栏状态

顶栏的引擎状态应来自全局运行 store：

- 空闲；
- 运行中；
- 已停止；
- 出错或取消后的非运行状态。

模式显示必须来自本次实际运行配置，而不是由 UI 临时切换推断。

### 9.2 通知按钮

Demo 的通知按钮没有实际行为。真实项目只有在存在通知数据源时才显示可操作状态：

- 如果没有通知中心，应移除按钮或将其作为不可用入口；
- 不得点击后无任何反馈；
- 不得显示虚假的未读数量。

### 9.3 刷新按钮

刷新必须重新读取相关真实数据，例如：

- 当前运行状态；
- LLM 配置；
- 当前简历；
- 历史记录；
- telemetry 汇总。

只更新时间文本不算刷新真实数据。

## 10. 明确禁止照搬的 Demo 行为

以下行为不得进入真实项目：

1. 用 `setInterval` 模拟后端运行。
2. 用固定 150 条作为真实队列总数。
3. 用定时 tick 增长扫描、生成、发送指标。
4. 运行中允许切换 Dry Run 和真实发送。
5. 用 `stop_run` 冒充暂停，并提供假的继续运行。
6. 在没有 IPC 支持时展示逐条审核并发送。
7. 将静态 `HISTORY` 作为真实历史记录。
8. 将固定成本和调用次数作为真实统计。
9. 将固定简历切片和召回样例作为真实解析结果。
10. 将固定环境体检和最近错误作为真实诊断。
11. 配置保存只更新 React 状态、不写入后端。
12. “复制日志”只弹 Toast、不实际写剪贴板。
13. 页面展示后端没有返回的岗位、公司、匹配度和批次字段。
14. 通过文案暗示“可回滚”“可恢复”“已发送”，但后端没有对应事实。

## 11. 真实项目的状态表达规则

界面中的每个状态都必须能回答“它来自哪里”：

| UI 状态 | 真实来源 |
| --- | --- |
| 是否运行 | `is_running`、store 状态、`loop_ended` |
| 当前岗位 | `job_found.payload.index` 等事件 |
| 岗位被跳过 | `job_skipped` |
| 招呼语已发送/模拟/拦截 | `letter_sent.payload.status` |
| 运行完成 | `loop_ended.reason = completed` |
| 运行取消 | `loop_ended.reason = cancelled` |
| 运行出错 | `error` 或 `loop_ended.reason = error` |
| 当前简历 | `get_resume` |
| AI 是否配置 | `get_llm_config.hasKey` 与 `model` |
| 环境字段 | `get_env_fields` |
| 历史招呼语 | `get_letters` |
| LLM 成本 | `get_telemetry_summary` |
| 问 AI 诊断文本 | `get_ai_help_report` |
| 日志目录 | `get_log_dir` |

如果某个 UI 状态没有对应来源，应删除该状态，或改为明确的“未知/未检查”。

## 12. 业务功能说明

### 12.1 Dry Run 的真实定义

Dry Run 不是前端审核模式，而是后端运行参数：

- 仍然读取岗位；
- 仍然抓取 JD；
- 仍然进行简历匹配；
- 仍然调用 LLM；
- 仍然校验招呼语；
- 仍然写入审计日志；
- 不点击真实发送按钮。

UI 可以把它设计成推荐的安全入口，但不能添加后端没有的逐条审核语义。

### 12.2 真实发送的真实定义

非 Dry Run 时，后端对校验通过的招呼语执行真实发送。真实发送不可撤回，UI 必须：

- 在启动前明确展示危险模式；
- 显示当前目标岗位标签；
- 保留二次确认；
- 运行中禁止修改发送模式；
- 显示后端实际返回的发送、跳过、拦截和错误结果。

### 12.3 校验失败与跳过

后端会对生成结果执行内容校验。校验失败的内容不会发送，并会写入审计日志。

UI 不得把以下情况混为“发送失败”：

- 岗位被匹配规则跳过；
- 招呼语校验失败；
- Dry Run 未发送；
- 真实发送成功；
- 运行被用户取消；
- 后端发生异常。

每种状态都应使用不同标签和解释。

### 12.4 取消与浏览器生命周期

`stop_run` 取消当前运行，但不会关闭 Chrome。`shutdown_browser` 才是关闭浏览器的独立操作。

UI 必须区分：

- 停止本轮任务；
- 关闭浏览器/完全重置；
- 下次运行复用已有登录态。

不得把“停止任务”文案写成“清理所有状态”或“关闭 Chrome”。

## 13. 实现验收清单

真实项目接入 Demo 视觉稿后，至少检查以下内容：

### 数据与状态

- [ ] 页面展示的数据都来自 IPC、store 或后端事件。
- [ ] 没有残留 Demo 固定数量、岗位、公司、时间和错误。
- [ ] 每个状态标签都能对应到后端来源。
- [ ] 空数据、加载中、错误、完成、取消状态都有明确表现。

### 运行安全

- [ ] 启动前遵守用户名、简历、Key、model 和重复运行校验。
- [ ] Dry Run 在启动时确定，运行中不可切换。
- [ ] 真实发送有二次确认。
- [ ] 没有把 `stop_run` 实现成假的暂停。
- [ ] 没有把中途取消显示为 100% 完成。

### IPC 与后端契约

- [ ] IPC 参数名与后端 command 一致。
- [ ] IPC 返回字段与 UI 类型一致。
- [ ] 事件类型和 payload 分支覆盖当前后端事件。
- [ ] 后端新增或删除字段时，页面不会静默使用旧假数据。

### 历史与配置

- [ ] 历史记录来自 `get_letters`。
- [ ] 成本统计来自 `get_telemetry_summary`。
- [ ] 配置保存调用真实 IPC 并在成功后重新读取。
- [ ] API Key 不进入 UI 日志或诊断文本。
- [ ] 配置字段以 `get_env_fields` 为准。

### 用户反馈

- [ ] 复制按钮实际写入剪贴板，并处理失败。
- [ ] 刷新按钮实际重新读取数据。
- [ ] 通知按钮有真实行为，或已移除。
- [ ] FAQ 文案中的操作在当前页面确实存在。
- [ ] 错误文案不承诺后端没有的恢复、回滚或审核能力。

## 14. 最终原则

迁移真实项目时，应优先保证：

1. 用户看到的状态真实；
2. 用户点击的按钮有真实后果；
3. 危险操作不会被 Demo 假状态掩盖；
4. 后端没有提供的数据不在 UI 中伪造；
5. UI 可以与 Demo 不同，但不能与后端事实冲突。

**一句话规则：**  
**把 Demo 当作界面草图和产品意图说明，把现有后端当作功能合同。**
